\section{Workflow Plan}

\subsection{Git Usage}
\begin{itemize}
	\item Github will be used as the primary version control system (VCS).
    \item All commits must be made to a non-master branch and submitted via a pull request before they can be merged.
    \item Branching Strategy: \begin{itemize}
    \item Main branch: Stable production-ready code waiting for a release.
    \item Documentation branches: Used to maintain and update project documentation and requirements.
        \begin{itemize}
            \item Notation: \texttt{docs/SL-<Issue\#>}
        \end{itemize}

    \item Development branch: Integration branch where all new features and bug fixes are merged. This branch will contain the latest features with the most up-to-date code. 
        \begin{itemize}
            \item Notation: \texttt{dev}
        \end{itemize}

    \item Feature branches: Used to develop and test new features before merging into the development branch. 
        \begin{itemize}
            \item Notation: \texttt{feature/SL-<Issue\#>}
        \end{itemize}

    \item Bugfix branches: Used to fix defects.
        \begin{itemize}
            \item Notation: \texttt{bugfix/SL-<Issue\#>}
        \end{itemize}
\end{itemize}
\end{itemize}

% TA Feedback (Git workflow plan): Expanded workflow details toward a Contributor's-Guide level (review rules, PR expectations, labels, and quality gates).
\noindent Additional workflow conventions (to support consistent contribution quality):
\begin{itemize}
    \item \textbf{Pull requests (PRs):} PRs should be small, scoped to one issue where possible, and include a short summary and test notes (what was validated).
    \item \textbf{Reviews:} At least one peer review is required before merging. Changes that affect authentication/authorization, payments, or database schema require review from the technical owner of that area.
    \item \textbf{Branch protection intent:} The main branch should only accept PRs that pass automated checks (lint/test/build) to reduce regressions.
    \item \textbf{Issue labeling:} Use consistent labels such as \texttt{documentation}, \texttt{feature}, \texttt{bug}, \texttt{chore}, \texttt{security}, and \texttt{frontend}/\texttt{backend}/\texttt{mobile} to improve filtering and ownership.
    \item \textbf{Definition of Done (DoD):} An issue is ``Done'' when the implementation is merged, basic tests are updated/added where applicable, and relevant documentation is updated (README or in-repo docs).
\end{itemize}

\section{Proof of Concept Demonstration Plan}

% TA Feedback (POC Demo plan): Added more project context so risks and the POC's purpose are clearer at this early planning stage.
\noindent This project delivers a centralized event platform for MES, spanning an attendee experience (registration/tickets/QR check-in) and an organizer experience (event setup, capacity rules, reporting). The proof-of-concept (POC) will demonstrate an end-to-end ``thin slice'' across the architecture to reduce early risk.

The primary risks of the project are as follows.
\begin{itemize}
    \item The ability to seamlessly integrate the system architecture components (i.e. frontend, backend, mobile app, database, APIs etc.).
    \item The ability of end users to intuitively use all features as intended.
% TA Feedback (POC Demo plan): Added additional early-stage risks (learning curve, third-party dependencies, and data/privacy constraints) to better connect the plan to realistic project success risks.
    \item The learning curve and time required to correctly implement payments, authentication/authorization, and database migrations without blocking progress.
    \item Reliability of third-party services (e.g., payment processor webhooks, notification delivery) and how failures affect user experience.
    \item Security and privacy constraints when handling attendee personal information, waivers, and auditability needs.
\end{itemize}

\noindent The proof-of-concept demonstration overcoming these risks will consist of.

\begin{itemize}
    \item A minimal but functional demo showcasing the different architecture layers working cohesively.
    \item A walkthrough showing a general end-user workflow (i.e. registering for events, paying for events, creating events, etc.).
% TA Feedback (POC Demo plan): Increased specificity so the demo is clearly tied to the risks and can be evaluated.
    \item A scenario-based demo: organizer creates an event with a capacity limit; attendee registers (and pays if ticketed); system issues a QR ticket; organizer scans/validates the ticket and the dashboard reflects attendance.
    \item A ``failure mode'' check: demonstrate how the system handles a failed payment or duplicate submission (no duplicate tickets; clear error messaging).
\end{itemize}

% TA Feedback (POC Demo plan): Added consequences/interpretation of a "failed" POC and immediate next steps (no detailed mitigation required, but evidence of thought).
\noindent A POC will be considered \textbf{failed} if the end-to-end slice cannot be demonstrated reliably (e.g., inconsistent database state across steps, inability to issue/validate tickets, or unclear ownership of integration boundaries), or if key third-party interactions (payments/webhooks) cannot be executed safely in a test environment. In that case, the team will treat the result as a signal to narrow scope to a simpler core workflow (e.g., RSVP-first with delayed payment), replace or defer a high-risk dependency, and prioritize stabilizing the API/database contract before adding additional features.

\section{Expected Technology}

\subsubsection*{Languages \& Frameworks} 
% TA Feedback (Eval Tools / LO13): Rewrote this subsection to justify each technology choice with project-specific pros/cons and limitations (not just a list).
The team will use \textbf{TypeScript (JavaScript + types)} as the primary language across the stack to reduce integration friction between the web app, mobile app, and backend while improving maintainability through static typing. The main limitation is added build configuration complexity and occasional type overhead during rapid prototyping, but this trade-off is justified by the size of the codebase and the need for reliable role/access-control logic.

% TA Feedback (Eval Tools / LO13): Added explicit rationale and trade-offs for the selected frameworks in the context of MES event workflows.
\begin{itemize}
  \item \textbf{Web: Next.js (React)} will be used for the organizer/admin dashboard because it supports fast development of data-heavy pages (tables, filters, analytics) and offers built-in routing and performance features (SSR/SSG) that help with perceived responsiveness. The primary drawback is additional framework conventions and deployment considerations compared to a simpler React SPA, but it aligns well with dashboard-style UX and iteration speed.
  \item \textbf{Mobile: React Native} will be used for the attendee-facing experience to prioritize a mobile-first workflow (ticket wallet, QR code, notifications) while sharing UI patterns and business logic with the React web code. The trade-offs include native module complexity (camera/QR scanning, push notifications) and platform-specific quirks; we mitigate this by keeping device-specific logic isolated and by validating early via proof-of-concept spikes.
  \item \textbf{Backend: NestJS (Node.js)} will be used because its opinionated architecture (modules, controllers, dependency injection) improves testability and helps enforce consistent structure across a multi-contributor student team. The main con is increased boilerplate compared to Express, but the structure is valuable for implementing non-trivial domains like payments, RBAC/FBAC, and event capacity rules.
\end{itemize}

\subsubsection*{Database \& ORM} 
% TA Feedback (Eval Tools / LO13): Expanded database/tool choice with justification and limitations relevant to event registration, reporting, and consistency.
The database will be \textbf{PostgreSQL}, self-managed via a Docker container for consistent local development and repeatable integration testing. PostgreSQL is well-suited for transactional workflows (ticket purchases, waitlists, check-in state) and supports relational constraints that help prevent overselling capacity. The main limitations are the operational overhead of schema migrations and environment management; we address this through automated migrations in CI and containerized local environments.

% TA Feedback (Eval Tools / LO13): Added pros/cons for ORM choice and how it impacts cross-group alignment.
For database access, the team is considering \textbf{Drizzle ORM} as a shared standard across groups because it provides strong TypeScript typing while staying close to SQL, which helps with performance and predictable queries for reporting/analytics. The trade-offs are a smaller ecosystem than more established ORMs and potential learning curve for contributors; we will mitigate this by documenting patterns (migrations, transactions) and keeping a clear boundary between domain logic and persistence.

\subsubsection*{Payments} 
% TA Feedback (Eval Tools / LO13): Added rationale and limitations for payments tech in context (student tickets, refunds, auditability).
Payments will be handled through \textbf{Stripe}, integrated using official SDKs, because it provides mature support for card payments, webhooks, refunds, and reconciliation---features that directly reduce organizer burden and improve auditability for MES events. Key limitations include reliance on third-party uptime and the need to secure webhook endpoints; we will isolate processor-specific logic behind a backend service boundary and use idempotency keys plus webhook signature verification to reduce double-charging risk.

\subsubsection*{Selected Libraries (initial)}
\begin{itemize}
% TA Feedback (Eval Tools / LO13): Clarified how each library will be used and why it fits, including trade-offs rather than naming options.
  \item \textbf{Frontend UI:} \textbf{Tailwind CSS} (preferred) or \textbf{Material UI} (fallback) to accelerate delivery of consistent UI components. Tailwind enables fast iteration and design consistency with low runtime overhead but can increase class verbosity; Material UI provides rich prebuilt components but can constrain visual customization and increase bundle size if not used carefully.
  \item \textbf{Backend:} NestJS modules for routing/validation to standardize API behavior and reduce input-handling defects; Stripe SDK for payments to minimize custom payment handling; Drizzle ORM for typed database access to reduce query bugs. The main limitation is dependency updates and version alignment across groups; we will pin versions per milestone and validate integration in a shared staging environment.
\end{itemize}

  \item \textbf{Sign-up capacity/hold logic} (e.g., bus/table/RSVP) to safely manage contention and inventory.

\subsubsection*{Dev Workflow \& Tooling}
\begin{itemize}
% TA Feedback (Eval Tools / LO13): Added rationale and limitations for workflow/hosting tools used during development and deployment.
  \item \textbf{Git + GitHub} will be used for version control and code review because PR-based workflows support traceability, peer review, and safer integration across multiple contributors. The main drawback is review overhead; we will mitigate by keeping PRs small and using issue templates/checklists.
  \item \textbf{GitHub Projects} will be used for sprint planning and visibility because it provides a shared source of truth for tasks across subteams. A limitation is that boards can drift from reality if not maintained; we will enforce updates during weekly planning and progress check-ins.

The trade-off is that operations (monitoring, backups, secrets management) are the team’s responsibility; we will start with a minimal staging environment and add operational safeguards (backups, environment variables, least-privilege access) as the project stabilizes.
\end{itemize}

\subsubsection*{Testing, CI/CD, and Performance} 
The team intends to adopt a layered testing strategy:
\begin{itemize}
  \item \textbf{Unit tests} for backend modules (NestJS services/controllers) and React components.
  \item \textbf{Integration tests} to validate backend endpoints against a local Postgres instance.
  \item \textbf{End-to-end (E2E) tests} for critical flows such as checkout, sign-ups, and access control.
\end{itemize}
Continuous Integration will be run through \textbf{GitHub Actions}, with pipelines for linting, type-checking, running automated tests, and validating database migrations.

\section{Coding Standard}

The team will adopt consistent coding standards to ensure readability, maintainability, and effective collaboration. For JavaScript code, the team will follow the \href{https://github.com/airbnb/javascript}{Airbnb JavaScript Style Guide}, which provides well-established conventions for formatting and best practices. Code formatting will be automated with \textbf{Prettier}, and linting will be enforced with \textbf{ESLint} to reduce inconsistencies across contributions.

Naming conventions will remain uniform across the stack:
\begin{itemize}
  \item \texttt{camelCase} for variables and functions
  \item \texttt{PascalCase} for React components and NestJS classes
  \item \texttt{snake\_case} for PostgreSQL tables and column names
\end{itemize}

Beyond style rules, the team will apply \textbf{Clean Code principles} to keep the codebase simple and easy to understand. This means writing small and focused functions, choosing descriptive names, avoiding duplication, and keeping modules cohesive. Comments will be added only where necessary to clarify complex logic, with the preference being self-explanatory code.

For version control, all work will be done in feature branches, with pull requests reviewed before merging into \texttt{staging} or \texttt{main}. Commit messages will follow the imperative style (for example, “Add payment processing logic”) to maintain a clear project history.

\section*{Appendix --- Reflection}

\begin{enumerate}
    \item Why is it important to create a development plan prior to starting the
    project?

    Creating a development plan helped the team align on goals, expectations, and responsibilities before beginning development. Because this project spans multiple groups, documenting decisions early established a common foundation and reduced the risk of misunderstandings later. It also encouraged us to think ahead about technologies, workflows, and risks, which gave the team more confidence moving into implementation.
    
    \item In your opinion, what are the advantages and disadvantages of using
    CI/CD?

    The advantages of CI/CD include automated testing, faster feedback, and reduced integration issues. It helps ensure that code changes are validated continuously, which improves reliability and makes collaboration smoother. On the other hand, the disadvantages are the upfront setup effort and the need for ongoing maintenance of pipelines. For a student project with limited time, the main challenge is balancing the investment in CI/CD with the need to deliver features quickly.
    
    \item What disagreements did your group have in this deliverable, if any,
    and how did you resolve them?

    The team did not have any major disagreements, but there were discussions around which ORM should be used. Some members had experience with Prisma, while others were interested in Drizzle for its modern features and close mapping to SQL. This process allowed the team to weigh different perspectives while still keeping flexibility in case future integration across groups requires adjustments.
