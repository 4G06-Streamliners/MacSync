\section{Functional Requirements Evaluation}

This section evaluates whether the Large Event Management System (LEMS) satisfies the functional requirements defined in the Software Requirements Specification (SRS). Functional requirements describe the expected behaviour of the system and define how users interact with the platform to perform tasks such as reserving tickets, completing event registrations, processing payments, requesting refunds, and managing user accounts.

The evaluation was performed using automated backend unit tests implemented with the Jest testing framework. These tests validate that controllers, services, and authorization guards behave correctly under both normal and edge-case conditions. The tests simulate realistic user actions and verify that the system enforces capacity constraints, maintains data integrity, and prevents unauthorized access.

The functional areas evaluated are:

\begin{itemize}
\item Ticket Reservation and Lockout
\item Payment Processing
\item Refund Request Management
\item User Management
\item Role-Based Access Control (RBAC)
\end{itemize}


\subsection{Ticket Reservation and Lockout (FR1)}

The ticket reservation subsystem ensures that event seats cannot be oversold and that users cannot reserve the same seat simultaneously. The system uses temporary reservations to lock seats during checkout while payment is being processed.

\paragraph{Test Case FR1-T01: Successful Seat Reservation}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T01-1

\textit{Initial State:} An event exists with available table seats and remaining capacity.

\textit{Input:} A user attempts to create a checkout session for a ticket.

\textit{Expected Output:} The system reserves an available seat, creates a reservation record, and generates a Stripe checkout session.

\textit{Test Case Derivation:} Ensures that the system correctly reserves seats before payment and prevents multiple users from selecting the same seat simultaneously.

\end{enumerate}


\paragraph{Test Case FR1-T02: Event Capacity Enforcement}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T02-1

\textit{Initial State:} The event has reached its maximum capacity.

\textit{Input:} A user attempts to reserve a ticket.

\textit{Expected Output:} The system returns an error message indicating that the event is full.

\textit{Test Case Derivation:} Confirms that the system correctly prevents ticket purchases once the capacity limit is reached.

\end{enumerate}


\paragraph{Test Case FR1-T03: Seat Lockout When No Seats Available}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T03-1

\textit{Initial State:} All table seats are reserved or locked by other users.

\textit{Input:} A user attempts to create a checkout session.

\textit{Expected Output:} The system returns an error indicating that no table seats remain.

\textit{Test Case Derivation:} Validates the seat lockout mechanism that prevents double booking.

\end{enumerate}


\paragraph{Test Case FR1-T04: Reservation Completion After Payment}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T04-1

\textit{Initial State:} A reservation exists associated with a Stripe checkout session.

\textit{Input:} The payment is successfully completed.

\textit{Expected Output:} The system creates a ticket record, assigns the seat to the user, records the payment, and deletes the temporary reservation.

\textit{Test Case Derivation:} Ensures that successful payments correctly finalize ticket registration.

\end{enumerate}


\paragraph{Test Case FR1-T05: Reservation Release}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T05-1

\textit{Initial State:} A temporary seat reservation exists for a checkout session.

\textit{Input:} The checkout session is cancelled or expires.

\textit{Expected Output:} The reservation is deleted and the seat becomes available again.

\textit{Test Case Derivation:} Confirms that seat reservations do not remain locked indefinitely.

\end{enumerate}


\paragraph{Test Case FR1-T06: Concurrent Reservation Handling}

\begin{enumerate}

\item \textbf{Test ID:} FR1-T06-1

\textit{Initial State:} Only one seat remains available for an event.

\textit{Input:} Two users attempt to reserve the final seat simultaneously.

\textit{Expected Output:} One reservation succeeds while the other receives an error indicating that no seats remain.

\textit{Test Case Derivation:} Verifies that the system prevents race conditions and maintains data consistency during concurrent access.

\end{enumerate}


\subsection{Payment Processing (FR2)}

The payment subsystem manages financial transactions associated with event ticket purchases. Payments are processed through the Stripe payment service and recorded within the system.

The functional tests verify that checkout sessions are created correctly, payments are recorded after successful transactions, and reservations are finalized into tickets once payment is completed.


\paragraph{Test Case FR2-T01: Checkout Session Creation}

\begin{enumerate}

\item \textbf{Test ID:} FR2-T01-1

\textit{Initial State:} An event exists with a valid Stripe price ID.

\textit{Input:} A user attempts to purchase a ticket.

\textit{Expected Output:} The system creates a Stripe checkout session and returns the session URL and session identifier.

\textit{Test Case Derivation:} Confirms that the payment service successfully initializes a Stripe checkout session for ticket purchases.

\end{enumerate}


\paragraph{Test Case FR2-T02: Payment Recording}

\begin{enumerate}

\item \textbf{Test ID:} FR2-T02-1

\textit{Initial State:} A Stripe payment has been completed successfully.

\textit{Input:} The system receives payment confirmation containing the Stripe payment intent ID and transaction details.

\textit{Expected Output:} The system records the payment in the database and associates it with the corresponding user, event, and ticket.

\textit{Test Case Derivation:} Ensures that successful payments are properly recorded for financial tracking and auditing.

\end{enumerate}


\paragraph{Test Case FR2-T03: Reservation Finalization After Payment}

\begin{enumerate}

\item \textbf{Test ID:} FR2-T03-1

\textit{Initial State:} A seat reservation exists for a user and a Stripe checkout session has been completed.

\textit{Input:} The system processes the successful payment event.

\textit{Expected Output:} The system creates a ticket, assigns the reserved seat to the user, records the payment, and deletes the temporary reservation.

\textit{Test Case Derivation:} Validates the full payment completion workflow from reservation to finalized ticket.

\end{enumerate}

\section{Nonfunctional Requirements Evaluation}

This section evaluates whether the system satisfies the nonfunctional requirements defined in the SRS and tested according to the VnV Plan. The evaluation covers performance, usability, and security compliance. Where formal quantitative testing (e.g., timed load benchmarks, structured usability studies) was not conducted within the project timeline, the evaluation describes the alternative evidence gathered through unit tests, developer testing, and informal usability sessions with external users.

The nonfunctional areas evaluated are:

\begin{itemize}
\item Performance
\item Usability
\item Security Compliance
\end{itemize}


\subsection{Performance (NFR1)}

Performance was evaluated through a combination of manual developer testing during implementation and automated unit-level concurrency tests. Formal timed benchmarking with a dedicated load-testing tool (as described in the VnV Plan) was not conducted due to time constraints; however, the system's responsiveness was validated through real-device testing with external users and the concurrent checkout stress tests described in Section~6.

\paragraph{Test Case NFR1-T01: Registration Workflow Responsiveness}

\begin{enumerate}

\item \textbf{Test ID:} NFR1-T01-1

\textit{Initial State:} Backend running locally with a seeded PostgreSQL database; Stripe test-mode payment integration enabled.

\textit{Input:} A developer manually completes the full registration workflow on a physical mobile device: browse events, select ticket, proceed to Stripe checkout, and receive ticket confirmation.

\textit{Expected Output:} The workflow completes without perceivable delay at each step. No timeouts or errors occur.

\textit{Test Case Derivation:} Provides a qualitative confirmation that the registration path is responsive under single-user conditions, addressing VnV Plan NFR1-T01.

\end{enumerate}


\paragraph{Test Case NFR1-T02: Concurrent Signup Handling}

\begin{enumerate}

\item \textbf{Test ID:} NFR1-T02-1

\textit{Initial State:} An event with exactly one table seat remaining.

\textit{Input:} Two checkout requests are fired concurrently via \texttt{Promise.all} in a Jest unit test (test SRL6).

\textit{Expected Output:} Exactly one request succeeds; the other receives an error. No duplicate tickets or seats are assigned.

\textit{Test Case Derivation:} Validates that the \texttt{FOR UPDATE SKIP LOCKED} mechanism handles concurrent access without data corruption. While this is a unit-level simulation rather than a full HTTP load test, it directly exercises the critical concurrency code path identified in VnV Plan NFR1-T02.

\end{enumerate}


\paragraph{Test Case NFR1-T03: Check-In Responsiveness}

\begin{enumerate}

\item \textbf{Test ID:} NFR1-T03-1

\textit{Initial State:} Event with valid tickets issued; QR scanner screen open on a physical device.

\textit{Input:} A valid ticket QR code is scanned at the event check-in screen.

\textit{Expected Output:} The check-in confirmation appears on the admin device without perceivable delay. The backend correctly marks the ticket as checked in (verified by unit tests TP6--TP9).

\textit{Test Case Derivation:} Confirms that the check-in flow is fast enough for practical use at event doors, as required by VnV Plan NFR1-T03.

\end{enumerate}


\subsection{Usability (NFR2)}

Usability was evaluated through informal testing sessions with peers from other capstone groups who had no prior exposure to MacSync. A formal structured usability study (as described in VnV Plan NFR3-T01) was not conducted within the project timeline; however, these sessions on physical mobile devices provided qualitative validation of the core workflows.

\paragraph{Test Case NFR2-T01: Registration Workflow Clarity}

\begin{enumerate}

\item \textbf{Test ID:} NFR2-T01-1

\textit{Initial State:} MacSync deployed on a physical mobile device; peers from other capstone groups acting as first-time users.

\textit{Input:} Users complete the event browsing, signup, and ticket purchase workflow without prior instruction.

\textit{Expected Output:} Users complete the workflow without confusion or assistance. No critical navigation or comprehension issues are observed.

\textit{Test Case Derivation:} Provides qualitative evidence that the registration flow is intuitive, partially addressing VnV Plan NFR3-T01-1. External users completed the workflow without requiring guidance.

\end{enumerate}


\paragraph{Test Case NFR2-T02: Feature Discoverability}

\begin{enumerate}

\item \textbf{Test ID:} NFR2-T02-1

\textit{Initial State:} MacSync mobile app running with bottom tab navigation.

\textit{Input:} Users navigate to event browsing, My Tickets, and profile screens.

\textit{Expected Output:} All primary features are accessible from the bottom tab bar without requiring multi-step navigation.

\textit{Test Case Derivation:} The tab-based navigation design ensures that core features are one tap away, addressing VnV Plan NFR3-T01-2. This was confirmed during peer testing sessions.

\end{enumerate}


\paragraph{Test Case NFR2-T03: Error Message Clarity}

\begin{enumerate}

\item \textbf{Test ID:} NFR2-T03-1

\textit{Initial State:} User interacts with the event signup screen.

\textit{Input:} User attempts to sign up for a full-capacity event or encounters a payment error.

\textit{Expected Output:} A clear error message is displayed explaining the issue (e.g., ``Event Full'', ``Payment failed''). The user is not left on a blank or broken screen.

\textit{Test Case Derivation:} Error handling is verified by frontend unit tests ES7 (full event error) and backend tests SRL2--SRL3 (lockout and capacity errors), addressing VnV Plan NFR3-T01-3.

\end{enumerate}


\subsection{Security Compliance (NFR3)}

Security was verified through automated unit tests for role-based access control and through architectural review of the payment and authentication subsystems. The RBAC guard tests (RBAC1--RBAC5) provide direct evidence that access control is enforced correctly.

\paragraph{Test Case NFR3-T01: Role-Based Access Control}

\begin{enumerate}

\item \textbf{Test ID:} NFR3-T01-1

\textit{Initial State:} Users with student and admin roles exist in the test environment.

\textit{Input:} Admin users access the Create Event screen; non-admin users attempt the same. Users request their own tickets and other users' tickets.

\textit{Expected Output:} Admin-only features are hidden from non-admin users. Users can access their own tickets but not other users' tickets (unless admin). Unauthorized requests are rejected.

\textit{Test Case Derivation:} Directly tested by automated unit tests RBAC1--RBAC5. Validates VnV Plan NFR4-T01.

\end{enumerate}


\paragraph{Test Case NFR3-T02: Sensitive Data Protection}

\begin{enumerate}

\item \textbf{Test ID:} NFR3-T02-1

\textit{Initial State:} System uses Stripe for all payment processing; user authentication handled via Clerk.

\textit{Input:} Review of the database schema and API responses for exposure of sensitive data.

\textit{Expected Output:} No credit card numbers, CVVs, or payment tokens are stored in the application database. Payment data is handled entirely by Stripe. User passwords are managed by Clerk and never stored by the application.

\textit{Test Case Derivation:} Architectural review confirms that the system delegates sensitive data handling to third-party services (Stripe, Clerk), satisfying VnV Plan NFR4-T03. The application database stores only Stripe session IDs and payment intent IDs for reference.

\end{enumerate}

\section{Automated Testing}
Automated testing forms the foundation of the verification process for the platform, as outlined in the VnV Plan.
The current implementation uses \textbf{Jest} with \textbf{ts-jest} for both frontend and backend, executed via GitHub Actions on each pull request.\\

\textbf{Backend tests} (run with \texttt{npm run test:backend} from the \texttt{test} directory) exercise NestJS controllers and services in isolation.
The suite includes unit tests for the users controller and service (including RBAC and role management), events controller and service, refund requests,
payments, and the roles guard. External dependencies such as Drizzle ORM and Stripe are mocked to ensure deterministic, fast execution. Coverage is
configured for the events, auth, and users modules. Tests are written in TypeScript with Jest mocks and a chainable database helper to simulate query results.\\

\textbf{Frontend tests} (run with \texttt{npm run test:frontend}) target the Expo React Native mobile app using a jsdom environment. The React Testing
Library is used to verify components and workflows such as event creation, the events screen, ticket details, refund requests, and QR scanning. React
Native, Expo Router, and other native modules are mocked so tests run in Node without a device or simulator. Coverage targets the
\texttt{src/frontend/mobile/app} directory.\\

\textbf{Continuous integration} is implemented with GitHub Actions. The CI workflow runs on pull requests and includes: backend lint and build (with
a PostgreSQL service container for migrations), backend unit tests, frontend unit tests, web-admin lint and build, and mobile type-checking and Expo
config validation. Test dependencies are installed from the dedicated \texttt{test} package, which also defines \texttt{npm run coverage:frontend} 
and \texttt{coverage:backend} for local coverage reporting.\\

This approach aligns with the VnV Plan's emphasis on Jest for the backend, automated CI execution, and separation of frontend and backend test suites.
 The frontend uses Jest rather than the originally planned Vitest; Cypress end-to-end tests and Supertest-based API integration tests are not yet in
  place. Static analysis (ESLint, Prettier, TypeScript) is applied in the backend and web-admin CI jobs, consistent with the plan's toolchain requirements.\\

\section{Code Coverage Metrics}
The VnV Plan specifies that the CI pipeline produce code coverage reports summarizing the percentage of tested lines and functions,
to be reviewed at the end of each sprint, with a goal of 75\% across all core modules. The current implementation supports coverage
collection via Jest's built-in instrumentation.\\

\textbf{Backend coverage} is configured in \texttt{test/backend/jest.config.js}. The \texttt{collectCoverageFrom} setting includes:
\begin{itemize}
\item \texttt{src/backend/src/events/**/*.ts} (excluding \texttt{*.d.ts} and \texttt{*.module.ts})
\item \texttt{src/backend/src/auth/**/*.ts}
\item \texttt{src/backend/src/users/**/*.ts}
\end{itemize}
Coverage reports are written to \texttt{test/coverage/backend}. The events, auth, and users modules correspond to the core backend logic for event management, RBAC, and user administration tested by the unit tests described in Section 6.\\

\textbf{Frontend coverage} is configured in \texttt{test/frontend/jest.config.js}. Coverage is collected from \texttt{src/frontend/mobile/app/**/*.\{ts,tsx\}}, excluding type definitions and \texttt{\_layout.tsx}. Reports are written to \texttt{test/coverage/frontend}. This scope aligns the mobile app screens (event creation, events list, ticket detail, refund requests, QR scanner) with the frontend tests.

Coverage is generated locally by running \texttt{npm run coverage:backend} and \texttt{npm run coverage:frontend} (or \texttt{npm run coverage} for both) from the \texttt{test} directory. The CI workflow currently runs the test suites without the \texttt{--coverage} flag; coverage reporting in CI and enforcement of the 75\% target can be added in a future iteration. The VnV Plan also mentions mutation testing to quantify the effectiveness of the test plan; mutation testing is not yet integrated into the build or CI pipeline.
